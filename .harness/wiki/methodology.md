# 方法论归纳

> 从项目规范和实践中提取的工作方法论。Agent 在需求/评审/复盘阶段按需查阅。

## 一、知识流动闭环

### 核心流程

```
用户问题 → 意图归类 → 路由加载 → 回答/实现 → 有结论? → 回填
```

### 回填规则（Phase 10 复盘时执行）

| 结论类型 | 写入位置 |
|---------|---------|
| 规格变更 | 对应 Atom PRD |
| 新术语 | glossary.md |
| 未定稿结论 | docs/pending/ |
| 流程改进 | Harness/rules/ |
| 可复用模式 | error-to-rule → coding-standards |
| 替代旧结论 | 旧文档加 `replaced_by` |

### 记忆层级

| 层级 | 含义 | 落点 |
|------|------|------|
| Working | 未加工的一手观察 | 当前对话、pending/inbox |
| Episodic | 会话压缩 | events.jsonl、专题 pending |
| Semantic | 跨会话可引用事实 | glossary、ontology、Atom PRD |
| Procedural | 可重复流程 | runbooks、capsules.json、genes.json |

### 变更检查清单

- [ ] 更新了最近索引？
- [ ] retrieval_order 需要新 question_type？
- [ ] 结论写入了 PRD/pending/进化事件？
- [ ] 旧文档加了 replaced_by？

## 二、PRD 写作规范

### 新方案标注规范

- 未上线方案：追加到文件末尾 `## ⚠️ 产品方案阶段（待实现）` 区块
- 进入立项后：合并进主体规则区，删除标注

### 大型重构 PRD 约定

- 单独建立原子 PRD，编号取最大+1
- 新 PRD 列出所有被影响的原子 PRD
- 被影响 PRD 头部标注重构方案链接

### 新增配置 PRD SOP

1. `config-registry.md` 补充一行
2. 配置 PRD 末尾追加 `## 影响功能`
3. 受影响功能 PRD 保持已有引用不变

## 三、产品方案设计方法论

### 五阶段流程

1. **理解问题** — 从用户痛点出发，先问"为什么难用"
2. **识别字段优先级** — 三问法：不配能否运行？强联动？有默认值？
3. **判断是否需双模式** — 用户诉求分化明显时触发
4. **设计高级设置分层** — 按业务语义分组，不做字段垃圾桶
5. **处理强条件联动** — 联动深度≥2 层时独立成步

### 字段归位三问

| 问题 | 是 | 否 |
|------|---|---|
| 不配就无法运行？ | 主流程必填 | 下一问 |
| 强条件联动？ | 主流程必填 | 下一问 |
| 有合理默认值？ | 高级设置（折叠） | 高级设置+说明 |

### 反模式

| 反模式 | 后果 |
|--------|------|
| 任务生成逻辑放高级设置 | 用户不知道必须配置 |
| 高频字段入高级设置 | 用户总是要展开 |
| 联动字段堆在一步 | 布局跳变 |
| 双模式维护独立组件 | 双倍开发成本 |
| 模式切换静默清空数据 | 用户不知道数据丢了 |

## 四、上下文工程原则

### 八项原则

| 原则 | 含义 | 在 Harness 中的体现 |
|------|------|-------------------|
| KV-Cache Friendly | 系统 prompt 前缀保持稳定 | Rules 文件不频繁变更 |
| Recitation | 末尾注入当前焦点避免迷失 | 每次回复开头说当前 Phase |
| Keep Wrong Stuff In | 不隐藏工具错误 | changes/ 保留失败记录 |
| Don't Get Few-Shotted | 打乱示例顺序 | 规则不机械复制 |
| File System as Context | PRD/profiles 从文件加载 | 产出物全部落文件 |
| Mask Don't Remove | 不动态增删工具 | 三层加载（不频繁切换） |
| Process-level Feedback | 精确到步骤归因 | 评审精确到文件:行号 |
| Evolution Assets | genes/capsules/events | 复盘时写入进化资产 |

## 六、探索优先原则

**规则**：功能设计和方案讨论时，不直接给结论，先探索、澄清、聚焦。

**做法**：
- 收到需求先问 1-2 个关键问题确认方向
- 给了参考时先描述"我看到了什么"让用户确认
- 复杂功能拆小步，每步确认后再进下一步
- 只有 bug fix 等明确任务才可直接执行

**WHY**：用户反馈"没有充分获取方向就给结论，非常不靠谱"。

## 七、测试过程基线（MIT 信息部）

> 来源：[测试过程基线](https://mi.feishu.cn/docx/Or93dg2aVoJPifxk95KcJ5JZnBX) — 各业务线结合业务特点和质量管理成熟度评估形成的强制基线。

### 六项测试规范

| 规范 | 核心要求 | Harness Phase |
|------|---------|--------------|
| 测试方案规范 | P0 项目必须有方案；关联 PRD；明确重难点；产研评审 | Phase 2 + Phase 5 |
| 测试用例设计规范 | 步骤完整可执行；正/逆/异常/隐性场景全覆盖；上下游标注数据流向 | Phase 5 |
| 测试用例评审规范 | 产研测三方参与；表述清晰不读 case；评审结论无异议发送纪要 | Phase 6 |
| 缺陷提报跟踪规范 | 关键信息完整；复现步骤准确；等级合理不乱标；及时跟踪验证关闭 | Phase 10 |
| 测试报告规范 | 含 case 通过率+缺陷遗留+测试结论；遗留问题三方确认 | Phase 8 |
| 线上验证规范 | 所有需求上线后必须验证；明确验证范围；测试数据标识后清理 | Phase 9 |

### 并入研发基线的 13 项指标

| # | 指标 | 计算/统计方法 | 工具 |
|---|------|-------------|------|
| 1 | 研发任务线上化率 | 线上化任务数/总任务数 | Meego + Matrix |
| 2 | 技术方案含影响范围 | 方案有"影响范围"章节 | Meego + 飞书 |
| 3 | 技术方案含可观测性 | 方案有"可观测性"章节 + Hera 监控 | Meego + Hera |
| 4 | 技术方案含风险评估 | 方案有"风险评估"或"失效分析"章节 | Meego + 飞书 |
| 5 | 代码变更须审查 | GitLab MR 有其他人 Approve | GitLab |
| 6 | 遵循编码规范 | CI 有代码扫描+安全扫描+Sonar | GitLab CI + Sonar |
| 7 | 自测执行率 | Teego 用例通过 或 单测覆盖率 | Teego / Sonar |
| 8 | 上线 Checklist + 评审 | Meego 关联 checklist + Matrix 审批 | Meego + Matrix |
| 9 | P0 项目测试方案 | Meego 节点有方案文档 | Meego |
| 10 | 测试用例须评审 | Teego 用例 / 文档用例 / 单测 | Teego / Sonar |
| 11 | 缺陷提报可跟踪 | 缺陷在 Meego 中提报并关联项目 | Meego |
| 12 | 测试报告 | Teego 报告 / 文档报告（含结论+风险） | Teego / 飞书 |
| 13 | 线上验证 | 测试计划中有线上验证用例 | Teego |

### 缺陷等级定义（禁止乱标 P0）

| 等级 | 定义 | 典型场景 |
|------|------|---------|
| P0 | 系统崩溃/核心流程完全不可用/数据丢失 | 生产宕机、资金损失、数据错乱 |
| P1 | 核心功能异常但有绕行方案 | 主流程报错可重试、关键字段显示错误 |
| P2 | 非核心功能异常/UI 问题 | 次要页面样式错乱、导出格式不对 |
| P3 | 体验优化/文案建议 | 按钮文字不直观、交互可优化 |

### 自测方式（三选一，推荐单测）

| 方式 | 工具 | 证明形式 |
|------|------|---------|
| 单测覆盖率（推荐） | Sonar | 覆盖率报告 |
| Teego 用例通过 | Teego | 关联需求的用例通过数 |
| 截图/录屏证明 | 手动 | 提测时提交截图 |
