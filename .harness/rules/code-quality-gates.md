# 代码质量四阶段门禁（FDE 质量保障标准）

> 权威阈值源。Phase 3/7/8 的扫描规则统一引用此文件，不再各自定义。
> 来源：FDE 产出质量保障测试方案 + MIT 研发基线。

## 核心原则

四道门禁逐级递进，**下层不过上层不跑**：

```
门禁1（代码扫描）→ 门禁2（单元测试）→ 门禁3（接口测试）→ 门禁4（E2E测试）
     ↓ 每次 commit          ↓ TDD 循环内           ↓ 涉及接口的任务        ↓ 提交 MR 前
```

---

## 门禁1：代码扫描（Phase 3 每次 commit 前）

**执行时机**：pre-commit hook，仅扫描本次变更的文件（增量）。
**反馈速度**：秒级，不打断 TDD 节奏。
**阻断行为**：commit 被拒绝，必须修复后重新 commit。

### 阻断标准（commit 失败）

| 维度 | 扫描内容 | 阻断条件 |
|------|---------|---------|
| **代码规范** | 格式、命名、死代码 | Critical / Blocker > 0 |
| **安全漏洞** | SQL 注入、XSS、硬编码密钥 | 高危 / 严重 > 0 |
| **代码复杂度** | 圈复杂度、函数长度 | 单函数圈复杂度 > 25 |
| **依赖安全** | 第三方依赖已知 CVE | 高危 CVE > 0 |

### 告警标准（不阻断，记录到 review）

| 维度 | 告警条件 |
|------|---------|
| 代码规范 | Warning 级别 |
| 安全漏洞 | 中低危 |
| 代码复杂度 | 单函数圈复杂度 > 15 |
| 依赖安全 | 中低危 CVE |

### 工具链

| 语言 | Linter | 阻断检查 | 自动修复 |
|------|--------|---------|---------|
| Java | Checkstyle + PMD | Critical/Blocker | Formatter 格式类 |
| TS/JS/React/Vue | ESLint + Prettier | error 级 | Prettier 格式类 |
| Python | Ruff | E/F 系列 | Ruff --fix 格式类 |
| PHP | PHP-CS-Fixer + PHPStan | Level 5+ | PHP-CS-Fixer 格式类 |

### 编码硬指标

| 指标 | 阈值 | 来源 |
|------|------|------|
| 文件长度 | ≤ 500 行 | Checkstyle / Linter |
| 方法长度 | ≤ 80 行 | Checkstyle / PMD |
| 方法参数数 | ≤ 7 个 | Checkstyle |
| if 嵌套深度 | ≤ 3 层 | Checkstyle |
| try 嵌套深度 | ≤ 2 层 | Checkstyle |
| 圈复杂度 | ≤ 15 (告警) / ≤ 25 (阻断) | PMD |
| 认知复杂度 | ≤ 15 | PMD / SonarLint |
| 类依赖数 | ≤ 20 | PMD |

### Git 提交规范

| 规则 | 阻断 |
|------|------|
| Conventional Commits 格式 | ✅ commit-msg hook |
| 零硬编码密钥/Token/API Key | ✅ pre-commit detect-secrets |
| 无已知漏洞依赖 | ✅ pre-push |

## 门禁2：单元测试（Phase 3 TDD 循环内）

**执行时机**：TDD 循环的 RED→GREEN 阶段，每个任务内持续执行。
**驱动方式**：Phase 3 TDD 强制模式（见 `development-process.md` Phase 3 TDD 段落）。

### 阻断标准

| 指标 | 阻断条件 | 说明 |
|------|---------|------|
| 测试通过率 | < 100% | 不允许有失败的单测 |
| 新增代码覆盖率 | < 80% | 只考核本次 MR 新增/修改的代码 |
| 核心模块覆盖率 | < 90% | 涉及资金、权限、核心业务逻辑 |
| 整体覆盖率变化 | 下降 > 2% | 防止大量无测试代码稀释覆盖率 |

### 强制规则

| 规则 | 原因 |
|------|------|
| 先写测试再写实现（TDD） | RED→GREEN→REFACTOR 循环 |
| 禁止跳过测试（skip / pending） | MR 中的 skip 计为未覆盖 |
| 测试必须有断言 | 空测试不计入覆盖率 |
| Mock 范围必须合理 | 不能把所有依赖都 Mock 掉 |

---

## 门禁3：接口测试（Phase 5 涉及接口的任务）

**执行时机**：Phase 5 中涉及接口变更/新增的任务。
**前置条件**：门禁1 + 门禁2 通过。
**详细规范**：`skills/testing/interface-testing.md`

### 阻断标准

| 指标 | 阻断条件 | 说明 |
|------|---------|------|
| 接口测试通过率 | < 100% | 所有接口用例必须通过 |
| 新增/变更接口覆盖 | 未覆盖则阻断 | 每个新增或修改的接口必须有测试 |
| 契约一致性 | 不一致则阻断 | 实际响应必须符合接口文档 Schema |
| 向前兼容检查 | 未标注则阻断 | 允许 breaking change，但必须显式声明 |

### 5 维度覆盖要求

| 维度 | 最低覆盖 |
|------|---------|
| 契约一致性 | 每个接口 ≥ 1 用例 |
| 业务逻辑 | 正向 + ≥ 1 异常分支 |
| 权限校验 | 无 token + 越权 各 ≥ 1 |
| 幂等性 | 写操作接口 ≥ 1 |
| 向前兼容 | 有 breaking change 时必须声明 |

## 门禁4：E2E 测试（Phase 6.8 本地执行，提交 MR 前）

**执行时机**：Phase 6.5 单测通过后，Phase 7 推送前。
**前置条件**：门禁1 + 门禁2 + 门禁3 全部通过。
**详细规范**：`development-process.md` Phase 6.8 段落。

### 阻断标准

| 指标 | 阻断条件 | 说明 |
|------|---------|------|
| P0 用例通过率 | < 100% | 核心路径一条不能挂 |
| P1 用例通过率 | < 95% 告警 | 不阻断但需说明原因 |
| 新功能 E2E 覆盖 | P0 未覆盖则阻断 | 新功能必须有对应 E2E 用例 |
| 执行稳定性 | 连续 3 次 flaky | flaky 测试必须 1 周内修复 |

### 覆盖策略

| 层级 | 覆盖范围 | 要求 |
|------|---------|------|
| **P0 核心路径** | 核心业务 happy path | 必须自动化，每次 MR 触发 |
| **P1 重要分支** | 关键异常路径 | 尽量自动化，至少手动执行 |
| **P2 辅助功能** | 非核心功能 | 手动测试，有变更时执行 |

### 不同场景执行方式

| 场景 | 执行内容 |
|------|---------|
| 新功能 | 为 P0 场景编写 E2E 用例 → 执行 → 确认通过 |
| Bug 修复 | 先写能复现 Bug 的 E2E 用例 → 修复 → 确认通过 |
| 回归验证 | 跑已有 P0 E2E 用例集 → 确认无回归 |

## 门禁与 Phase 映射总表

| 门禁 | 嵌入 Phase | 频率 | 反馈速度 | 执行者 | 审查者 |
|------|-----------|------|---------|--------|--------|
| 门禁1 | Phase 3（每次 commit 前） | 高频 | 秒级 | pre-commit hook 自动 | Tech Lead |
| 门禁2 | Phase 3（TDD 循环内） | 高频 | 秒级 | FDE/AI Agent | Reviewer (Phase 6) |
| 门禁3 | Phase 5（涉及接口的任务） | 中频 | 秒-分钟级 | FDE/AI Agent | Reviewer (Phase 6) |
| 门禁4 | Phase 6.8（MR 前） | 低频 | 分钟级 | FDE/AI Agent | Reviewer |

## 与 Superpowers 的协同

| Superpowers Skill | 关联门禁 | 协同点 |
|-------------------|---------|--------|
| brainstorming | 门禁3、4 | 需求阶段识别接口变更点和 E2E 测试要点 |
| writing-plans | 门禁2、3 | 任务拆分时标注「单测任务」vs「接口测试任务」 |
| test-driven-development | 门禁2、3 | 驱动 TDD 循环（RED→GREEN→REFACTOR） |
| verification-before-completion | 门禁1、2、4 | 汇总检查覆盖率 + 执行 E2E（门禁4） |
| requesting-code-review | 全部 | 提交 MR 时附带四道门禁通过证据 |
