# 抗合理化检查表

> 来源：PUA 方法论——防的不是外部攻击，是**自己骗自己**。
> Confidence Gate 防"不确定时猜测"，本表防"觉得确定但其实是自我欺骗"。
> 触发时机：Phase 4 评审 + Phase 10 归档 + 任何标记"已完成"的时刻。

## 检查表

| 借口 | 反击 | 验证方法 |
|------|------|---------|
| "已完成" | 验证命令跑了吗？输出贴了吗？ | 必须有命令 + 输出截图/文本 |
| "已修复" | 修复前 vs 修复后的对比证据呢？ | 必须有 before/after 差异 |
| "超出能力范围" | 试了几条路？覆盖几个维度？ | 列出 ≥3 条本质不同的尝试 |
| "可能是环境问题" | 你验证了吗还是猜的？ | 必须有环境检查命令输出 |
| "差不多就行" | 验收标准全过了吗？ | 逐条 AC 对照 |
| "我无法解决" | 走完 5 步调试法了吗？ | 闻味道→揪头发→照镜子→执行→复盘 |
| "建议用户手动处理" | 你缺乏 owner 意识 | 先穷尽自动化方案 |
| "这个改动量太大" | 是真的大还是方案不对？ | 铁律 #29 代码量合理性检查 |
| "系统就是这样的" | PRD 说应该是什么？代码行为≠正确行为 | 引用 PRD 原文对比（prd-code-alignment 协议） |
| "应该是设计如此" | 你查了 PRD 还是在猜？ | 查 PRD + ontology + 字段定义，给出原文 |
| "可能是手动操作的" | 你验证了 taskSource/createBy 字段吗？ | 查数据字段证明来源，不猜 |
| "代码逻辑就是这么写的" | 代码可能有 Bug，PRD 才是标准 | 查 PRD 定义，对比代码实现 |
| "看起来正常/符合预期" | 谁的预期？PRD 的还是你的？ | PRD 原文引用 + 观察值对比 |

## 执行规则

```
标记"已完成/已修复/PASS"之前：
1. 扫描上方 8 条，命中任一借口 → 执行对应验证方法
2. 验证不通过 → 不标记完成，继续执行
3. 验证通过 → 标记完成，附上验证证据

Phase 4 评审时：
  → 检查 code-review.md 中是否有未验证的声明
  → "功能正确" 但没有运行输出 = 命中第 1 条

Phase 10 归档时：
  → 检查 retrospective.md 中是否有"差不多/大概/应该"等模糊词
  → 有 → 追问具体验证证据
```

## 失败升级机制（Level 0-4）

> 来源：Agent Soul 执行内核。与 SOP-H3 互补：SOP-H3 说"失败 2 次换思路"，本表说"怎么升级"。

| Level | 触发条件 | 强制动作 |
|-------|---------|---------|
| **L0 正常执行** | 初始状态 | 最小修改 + 快速验证 |
| **L1 同一路径失败 2 次** | 连续 2 次微调无效 | 停止微调，改用本质不同的方案（猜测→读源码、局部修补→追调用链、手工→最小复现） |
| **L2 仍未解决** | L1 方案也失败 | 逐字读错误信号 → 搜索代码/文档/历史 → 读失败位置上下文 → 列 ≥3 假设逐个验证 → 反转主假设 |
| **L3 问题复杂或影响大** | L2 + 涉及线上/发布/数据 | 完整检查清单：错误日志✓ 仓库搜索✓ 配置/依赖/版本/权限/路径✓ 最小复现✓ 上下游影响✓ 不同技术路径✓ 成功标准✓ |
| **L4 穷尽后仍无法完成** | 以上全走完 | 输出结构化失败报告（见下方模板），不空泛说"无法解决" |

> **量化版（G5）**：本表 L1 触发条件「同一路径失败 2 次」由 [`loop-break-quantified.md`](loop-break-quantified.md) 落到机械门禁——`tools/governance/verify-counter.sh` 持久化 `(task_id, axis_id) → count`，count≥2 自动 prompt 换路，count≥3 + enforce 模式必须 `--force-same-axis="<reason>"` 才能继续，且自动写入 dream-queue 周复盘。软规则 + 硬计数器共同生效。

## Owner 四问

> 每次任务交付前至少回答这 4 个问题：

1. **根因是什么？**（不是表面现象）
2. **还有谁会被影响？**（上下游、同类场景）
3. **如何降低同类问题再次发生的概率？**（预防措施）
4. **当前结论的证据是什么？**（命令输出、日志、对比）

## 五步调试法（穷尽一切的标准流程）

> 源自阿里三板斧，标记"我无法解决"前必须走完。

| 步骤 | 名称 | 核心动作 |
|------|------|---------|
| 1 | **闻味道** | 列出所有尝试，找共同失败模式 |
| 2 | **揪头发** | 逐字读错误 → WebSearch → 读源码 → 验证环境 → 反转假设 |
| 3 | **照镜子** | 是否重复犯错？是否搜了？最简单的可能检查了吗？ |
| 4 | **执行** | 新方案必须本质不同，有验证标准，失败时产出新信息 |
| 5 | **复盘** | 什么解决了？为什么之前没想到？主动检查关联问题 |

## 体面的退出（穷尽后的结构化失败报告）

穷尽一切后仍无法解决，输出的不是"我不行"，而是**可交接的知识资产**：

```markdown
## 结构化退出报告

### 已验证事实
- {事实 1}（验证方法：{命令/截图}）
- {事实 2}

### 已排除可能
- {排除项 1}（排除原因：{证据}）

### 缩小范围
- 问题锁定在：{具体范围}

### 推荐下一步
- {建议 1}
- {建议 2}

### 交接信息
- 相关文件：{路径}
- 关键日志：{位置}
- 已尝试方案：{清单}
```
