# PRD-Code 对齐协议（全阶段注入）

> 来源：CASE-087（自盘任务按 user_code×use_dept_code 拆分，PRD 明确只按 user_code）
> 核心教训：**观察到的系统行为 ≠ 正确行为。PRD 说什么才是什么。**
> 注入时机：Phase 1 需求分析 + Phase 3 编码 + Phase 6.8 E2E + Phase 9 部署验证

---

## 铁律

```
系统当前行为 ≠ 正确行为
PRD 定义 = 正确行为的唯一来源
代码实现 = 需要被验证的对象，不是参考答案
```

**三个致命错误**（本协议专门防止）：

| # | 错误模式 | 反击 |
|---|---------|------|
| 1 | 观察到数据特征后，直接用代码行为"解释"为合理 | **停。先问：PRD 说应该是什么？** |
| 2 | 不确定时猜测"可能是手动操作的/可能是设计如此" | **停。查 PRD/ontology/字段定义，禁止猜。** |
| 3 | E2E 测试中把所有现状标为 PASS（因为"系统跑出来就是这样"） | **停。每条数据对照 PRD 验收标准判定。** |

## 各 Phase 注入规则

### Phase 1 需求分析

**接收需求时**，必须执行 PRD-Code 预对齐：

```
对需求涉及的每个业务规则：
  1. 找到 PRD 原文定义（精确到段落/Gherkin）
  2. grep 代码找到对应实现
  3. 对比：实现是否完全符合 PRD？
  → 不符 → 标记为"PRD-Code 偏差"，写入 requirement.md
  → 符合 → 标记为"已验证一致"
```

### Phase 3 编码实现

**动手前**，对修改涉及的每个方法：

```
问三个问题：
  Q1: 这个方法实现的业务规则在 PRD 哪里定义？
  Q2: PRD 的完整描述是什么？（不是我记忆中的，是原文）
  Q3: 当前代码是否已经完全符合 PRD？（可能有既存偏差）
```

### Phase 6.8 E2E 本地测试（核心加固点）

**每次观察到数据时**，执行 PRD 对照检查：

```
┌─ 观察到数据特征（数量/分布/状态/字段值）
│
├─ Step 1: 这个特征是否"看起来正常但需要验证"？
│   → 任何非 trivial 的数据特征都需要验证
│   → "同一用户有 2 个任务" = 非 trivial
│   → "列表为空" = 非 trivial（除非 PRD 说应该为空）
│
├─ Step 2: PRD 说应该是什么？
│   → 打开对应 PRD/requirement.md/Gherkin
│   → 找到该维度的定义（原文引用）
│   → 记录：PRD 原文 = "xxxxx"
│
├─ Step 3: 对比
│   → 观察值 vs PRD 定义
│   → 一致 → PASS，记录证据
│   → 不一致 → DEVIATION，立即报告
│
└─ Step 4: 输出
    → e2e-evidence.md 中每条记录必须有：
      观察值: xxx
      PRD 定义: "原文引用"
      判定: PASS / DEVIATION
```

**禁止行为**：
- ❌ "系统返回了 2 条，应该就是 2 条" → 这是循环论证
- ❌ "可能是用户手动创建的" → 这是无证据猜测
- ❌ "代码逻辑这样写的，所以应该是这样" → 代码可能有 Bug

**正确行为**：
- ✅ "系统返回了 2 条。让我检查 PRD..."
- ✅ PRD: "盘点方式为自盘时，按资产台账上的 user_code 维度拆分盘点任务"
- ✅ "PRD 说只按 user_code，不应该有 2 个任务。判定：DEVIATION。"
- ✅ 立即进入根因分析

### Phase 9 部署后验证

**同 Phase 6.8 规则**，对线上数据同样执行 PRD 对照检查。线上环境更容易出现"既有数据的历史偏差"，更需要 PRD 作为判定标准。

## E2E 证据模板（强制格式）

Phase 6.8/9 的 `e2e-evidence.md` 中，每个验证点必须包含：

```markdown
### FP-XX: [场景名称]

**操作**：[执行了什么]
**观察**：[看到了什么数据/现象]
**PRD 定义**：> [PRD 原文引用，精确到段落]
**判定**：✅ PASS / ❌ DEVIATION
**证据**：[命令输出/截图/数据]
```

如果"PRD 定义"字段为空或写"N/A" → 该验证点无效，门禁不通过。

## 触发词检测（hook 可用）

以下短语出现在 AI 输出中时，触发 PRD 对照警告：

| 触发词 | 含义 | 应该做的 |
|--------|------|---------|
| "应该是这样的" | 未验证的断言 | 查 PRD 给出依据 |
| "可能是手动/设计如此" | 无证据猜测 | 查数据字段（taskSource/createBy）+ PRD |
| "代码就是这么写的" | 循环论证 | 代码可能有 Bug，查 PRD |
| "看起来正常" | 未经验证的判定 | 给出 PRD 原文对比才算"正常" |
| "符合预期" | 谁的预期？ | PRD 的预期 ≠ 你的预期 ≠ 代码的预期 |

## 失败案例（CASE-087）

```
场景：自盘任务生成 E2E 验证
观察：qinyanshan 用户有 2 个盘点任务

错误响应（实际发生的）：
  → "自盘按 user_code 和 dept 维度拆分"
  → "可能是手动拆分的"
  → 直到用户反复追问才查代码

正确响应（应该做的）：
  → "qinyanshan 有 2 个任务。让我检查 PRD..."
  → PRD: "盘点方式为自盘时，按资产台账上的 user_code 维度拆分盘点任务"
  → "PRD 说只按 user_code，不应该有 2 个任务。判定：DEVIATION。"
  → 立即进入根因分析
```
