# 代码变更分析门禁（Phase 3 注入）

> 注入时机：**所有涉及现有系统的代码变更**（修 Bug / 修改功能 / 新增功能）
> 来源：CASE-084（幂等修复破坏多车添加）、CASE-086（data-sync 赋值错误根因分析范例）
> 配套方法论：`skills/debugging/SKILL.md`（系统化调试四阶段，提供根因调查具体方法）
> 核心原则：**不能说清楚 = 没想清楚 = 没查清楚。写不出报告 = 不许动手写代码。**

---

## 适用范围

| 场景 | 是否适用 | 说明 |
|------|---------|------|
| 修 Bug | ✅ | 全量适用（含根因定位） |
| 修改现有功能 | ✅ | 用"变更分析"模板替代"根因"模板 |
| 在现有系统新增功能 | ✅ | 必须分析接入点、数据流、影响面 |
| 全新项目从零开始 | ❌ | 用 brainstorming + writing-plans |

## 门禁流程

### Inner Loop 与变更分析门禁的关系

> Inner Loop（`bin/inner-loop.sh --run`）是**门禁失败时的自动消化层**，与本协议互补不替代：

| 门禁步骤 | 失败信号 | Inner Loop 反应 | scope 选择规则 |
|---|---|---|---|
| ①复现 / ①现状分析 | 三定位问题缺答、调用链未追到底、变更点不清 | self-reflect 给出 cause/fix_hint → micro retry 让 agent 补齐 | 如 cause 含"调用链/触发点未确认/根因不明" → micro |
| ②根因报告 / ②审查 | 报告 5 段缺漏、PRD 场景未列全、与 evidence 矛盾 | reflection-validator 校验 cause 命中证据 → 拒幻觉重写 | 反思双次幻觉 → pivot |
| ③/④测试 | 单测 / E2E 不绿 | micro retry ≤ 2 次（修代码或补 case）；仍失败 → pivot | cause 含"重构/方案需重设计/pivot" → 强制 pivot |

**核心约束**：Inner Loop 不替代①②③④四步硬约束。`status=blocked` 后仍需人工按本协议模板补齐报告，不允许"反思一下就跳过门禁"。

详见 `evolution/reflexion.md §1`。

### Bug 修复：四步门禁

| 步骤 | 硬约束 | 阻断条件 | 验证输出 |
|------|--------|---------|---------|
| ①复现 | 端到端跟踪完整调用链 | 未回答三个定位问题 → **禁止写修复代码** | `[H10-复现] 链路：触发→...→发送` |
| ②根因报告 | 输出结构化根因分析（5 段模板） | 未输出完整报告 → **禁止写修复代码** | `[H10-根因] 见下方模板` |
| ③审查 | 读修改方法的 PRD + 列出全部业务场景 | 未列出场景 → **禁止提交修复** | `[H10-审查] 场景：1.xxx 2.xxx，修复兼容全部` |
| ④测试 | 本地跑单测通过 | 测试不绿 → **禁止 git push** | `[H10-测试] X tests passed, 0 failures` |

### 功能变更/新增：三步门禁

| 步骤 | 硬约束 | 阻断条件 | 验证输出 |
|------|--------|---------|---------|
| ①现状分析 | 输出结构化变更分析报告（5 段模板） | 未输出完整报告 → **禁止写代码** | `[H10-分析] 见下方模板` |
| ②审查 | 读修改方法的 PRD + 列出全部受影响场景 | 未列出场景 → **禁止提交** | `[H10-审查] 影响场景：1.xxx 2.xxx` |
| ③测试 | 本地跑单测通过 | 测试不绿 → **禁止 git push** | `[H10-测试] X tests passed, 0 failures` |

## 根因报告模板（Bug 修复用）

> 来源：CASE-086 — 一行赋值错误导致数据权限过滤缺失 50% 记录

动手写修复代码前，必须输出以下 5 段（可长可短，但每段不能省）：

```
### 1. 业务场景
- 涉及哪些字段/实体/功能？
- 这些字段被谁消费？（下游依赖：权限过滤/报表/接口/页面）
- 用户视角的症状是什么？

### 2. 逻辑展开
- 相关方法的算法步骤（伪代码或编号列表）
- 数据从输入到输出的完整流转路径

### 3. Bug 所在
- 精确到文件:行号
- 期望行为 vs 实际行为（before/after 对比）

### 4. 影响链
- 从 Bug 点到用户可见症状的完整因果链
- 格式：Bug → 中间状态1 → 中间状态2 → 用户症状

### 5. 影响范围
- 为什么是 X% 而不是 100%？（或为什么是 100%？）
- 有哪些写入路径？哪些受影响、哪些不受？
- 受影响的数据量/用户量估算
```

## 变更分析报告模板（功能修改/新增用）

> 核心原则：你不能安全地修改你不完全理解的东西。

动手写代码前，必须输出以下 5 段：

```
### 1. 现状梳理
- 要修改/接入的模块当前做什么？服务谁？
- 核心方法的算法步骤（伪代码或编号列表）
- 数据从输入到输出的完整流转路径

### 2. 变更点
- 精确到文件:方法（新增）或文件:行号（修改）
- 变更前 vs 变更后的行为对比
- 如果是新增：接入点在哪？数据从哪来、到哪去？

### 3. 影响面分析
- 该方法/接口被谁调用？（grep 调用方，列全）
- 每个调用方在变更后是否仍然正确？逐一过
- 有无共享状态（缓存/数据库字段/消息队列）被影响？

### 4. 边界与风险
- 空值/空列表/并发/幂等/大数据量 — 各场景是否覆盖？
- 是否有向后兼容问题？（老数据、老接口、老版本客户端）
- 失败场景：如果新代码抛异常，上下游会怎样？

### 5. 验证策略
- 用什么测试证明变更正确？（单测 case 设计思路）
- 如何验证没有破坏已有功能？（回归范围）
- 线上灰度/回滚方案是什么？
```

## 判断标准

- 报告中出现"大概"、"可能"、"不太确定" → **调查不充分，继续挖**
- 影响面分析中只列了 1 个调用方但 grep 发现有 5 个 → **不完整，补全**
- 边界分析写"应该没问题" → **不是分析，是猜测，重做**

**反面教材**：直接说"改一下这里应该就好了"然后动手 → 这不是工程，是赌博。

## ①复现的三个定位问题（必须全部回答才能动手）

> 来源：CASE-085（定位到错误仓库/方法，浪费 30 分钟）
> 调查方法：加载 `skills/debugging/SKILL.md` 第一阶段（分层诊断 + 反向追踪）

1. **用户收到的是什么？**（飞书消息 / 工作台待办 / 邮件 / 短信 / 小程序推送）
2. **什么动作触发了它？**（提交时 / 审批通过后 / 入库确认后 / 定时任务 / 其他）
3. **从触发动作到最终发送的完整代码路径？**（追踪调用链直到找到实际发送行）

```
反面教材（CASE-085）：
  问题："内领通知发错人"
  错误做法：搜"通知" → 找到 entry-be saveTask() → 改了 → 不是真正发飞书的地方
  正确做法：
    Q1: 飞书消息（非工作台待办）
    Q2: 资产入库确认后触发
    Q3: stock-be processInternalWithdraw() → confirmStockAsset() → sendInternalCollectionMsg():2161
```

## 场景审查 Checklist

修改一个方法/函数前回答：
- 这个方法被谁调用？（grep 调用方）
- 它服务哪些业务场景？（读 PRD）
- 我的修改是否兼容所有场景？（逐一验证）
- 边界 case：空列表？多条记录？并发调用？
