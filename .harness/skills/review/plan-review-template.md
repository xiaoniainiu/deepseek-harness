# 计划评审模板

## 审查维度

| 维度 | 检查点 | 研发基线 |
|------|--------|---------|
| 需求完整性 | 验收标准是否可测试？边界是否定义？ | — |
| 需求关联 | 是否关联了需求号/Meego？ | 基线 1 |
| 影响范围 | 业务上下游 + 技术上下游是否覆盖？ | 基线 2 |
| 可观测性 | 方案是否包含监控/告警/日志设计？ | 基线 3 |
| 失效分析 | 业务风险 + 技术风险是否列出？降级方案？ | 基线 4 |
| 架构适配 | 涉及的层是否完整？是否违反层间规则？ | — |
| 数据影响 | 是否需要新表/新列？是否影响现有数据？ | — |
| 外部依赖 | 是否涉及新的外部调用？接口文档是否确认？ | — |
| 测试策略 | 如何验证？自动化还是手动？覆盖哪些场景？ | 基线 7/9 |
| 上线方案 | 上线步骤/回滚步骤/配置变更/上线窗口？ | 基线 8 |

### 技术设计评审维度（Phase 2.3 触发时追加）

> 来源：MIT 技术设计方案标准 V1.7。仅在 Phase 2.3 技术设计方案评审时使用。

| 维度 | 检查点 | MIT V1.7 章节 |
|------|--------|-------------|
| 设计完整性 | 十章是否全覆盖？不涉及的是否标注了原因？ | 全部 |
| 架构合理性 | 模块边界清晰？职责划分明确？通信方式合理？架构图是否提供？ | §2 架构设计 |
| 接口兼容性 | 新旧接口向后兼容？版本策略？MiAPI 链接是否提供？ | §3 接口设计 |
| 外部依赖确认 | 依赖的外部服务接口文档是否已确认？超时/重试策略？ | §4 外部依赖 |
| 领域设计 | 领域分解是否合理？关键流程有可视化图？ | §5 内部设计 |
| 数据迁移 | schema 变更的 DDL + 回滚 SQL 是否提供？数据安全是否评估？ | §6 数据设计 |
| 部署策略 | 灰度比例/持续时间？回滚触发条件？上线步骤是否清晰？ | §7 部署/运维 |
| 监控覆盖 | 业务指标 + 技术指标是否定义？报警阈值和方式？ | §8 监控报警 |
| 设计难点 | 每个难点是否有对应的应对措施或需要的支持？ | §1.3 设计难点 |
| 术语一致 | 术语表与 requirement.md / glossary 是否一致？ | §1.4 术语定义 |

## 与多视角评审的关系 [C3]

本模板提供 **审查维度清单**（10 项检查点），`skills/review/multi-perspective.md` 提供 **五视角执行协议**（产品/技术/风险 + 战略/设计按路由表条件触发）。

- 模式 A/B 需求：**同时使用两者**——先用本模板逐项检查，再用多视角评审补充产品和风险维度
- 模式 C 需求：只用本模板即可，多视角评审可选
