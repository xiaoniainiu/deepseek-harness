# Brainstorming — 苏格拉底式需求探索

> Phase 1 前半段。在写 PRD 之前，先通过结构化对话厘清真正要做什么。
> 来源：Superpowers brainstorming skill + Harness feedback_exploration-first

## 触发条件

- Phase 1 开始时（任何创造性工作之前）
- 用户给出需求描述但细节不足时

## 铁律

1. **设计未获批准前，禁止写任何代码**
2. **一次只问一个问题** — 不要列 5 个问题让用户批量回答
3. **每个问题优先给选项** — 多选题 > 开放题
4. **最简项目也走完探索** — 自认为"很简单"时才最容易犯错

## 探索流程

### Step 0：需求分级（新增）

> 在探索任何细节之前，先判定需求级别，决定走哪条路。

1. 根据路由表（`README.md` §需求分级路由）判定需求级别（L1-L4）
2. 向用户确认："我判断这是 L{N} {类型}需求，因为 {理由}，你同意吗？"
3. 按级别路由：

| 级别 | 路由 |
|------|------|
| **L1 探索型** | → `idea-exploration.md`（完整 6 追问）→ 回到 Step 3 |
| **L2 新建型** | → `idea-exploration.md`（精简 3 追问）→ 回到 Step 3 |
| **L3 增强型** | → 直接进入 Step 1 上下文探索（原有流程） |
| **L4 修复型** | → 直接进入 Step 2 逐步澄清（可简化） |

**降级保护**：AI 判定的级别只能被用户**升级**（L3 → L2），不能降级（L2 → L3）。

L1/L2 从 `idea-exploration.md` 返回时，已有 `exploration.md`（含推荐方案和用户选择），直接进入 Step 3 方案提出（基于探索结论细化）。

### Step 1：上下文探索

在提问之前，先自己读：
- 项目 README / CLAUDE.md
- 相关模块的代码结构
- 最近的 git 提交

目标：了解够多再提问，不问已有答案的问题。

### Step 2：逐步澄清（一次一个）

按以下顺序逐步提问，每次只问一个：

1. **目标**：用户想解决什么问题？（不是"想加什么功能"）
2. **现状**：现在怎么处理的？痛点在哪？
3. **约束**：有什么不能动的？时间/技术/组织上的限制？
4. **范围**：什么在范围内？什么明确不做？

### Step 3：方案提出（2-3 种）

厘清需求后，必须提出 **2-3 种方案**：

```
方案 A：[描述] — 优点 / 缺点 / 适合场景
方案 B：[描述] — 优点 / 缺点 / 适合场景
方案 C：[描述] — 优点 / 缺点 / 适合场景（可选）

推荐：方案 X，因为 [理由]
```

禁止只给一种方案然后问"行不行"。

### Step 4：分段确认

不要一次把整个设计全倒出来。分段展示，每段获得用户确认后再继续：

1. 先展示数据模型 / 实体关系 → 确认
2. 再展示业务流程 / 状态流转 → 确认
3. 最后展示接口设计 / 前端交互 → 确认

### Step 5：歧义标记

发现 PRD 描述不明确的地方，编号标记 + 给选项：

```
待确认：
1. 删除后是否可恢复？ A.软删除 B.硬删除
2. 权限粒度？ A.模块级 B.按钮级 C.数据行级
```

用户可快速回复"1A, 2B"。

## YAGNI 原则

在探索过程中持续挑战需求范围：
- "这个功能第一版必须有吗？"
- "如果不做 X，用户能用其他方式解决吗？"
- "最简版本是什么样？"

砍掉投机性功能，聚焦最小可交付范围。

## 已有系统优化的特殊规则

当需求是优化已有系统（而非新建功能）时：

1. **先诊断后开药** — 不读代码就提方案 = 庸医
2. **先保护后动刀** — 第一个任务必须是添加保护性测试/基准测试
3. **最小化改动** — 增量修改，不重写整个系统
4. **基准对比** — 每步完成后与基准对比，退化立即回滚

## 输出

探索完成后：
1. 进入 `prd-to-ai-ready.md` 生成结构化附录
2. **验收标准必须使用 `spec-format.md` 格式**（SHALL/MUST + Given/When/Then 场景）
3. 输出 `requirement.md`
4. 输出后自动触发 `spec-validation.md` 进行程序化验证
