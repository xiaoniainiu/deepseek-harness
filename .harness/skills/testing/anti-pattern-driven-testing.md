# 反模式驱动测试（Anti-Pattern Driven Testing）

> Phase 5 标准步骤。从 anti-patterns.md 中扫描与本次变更相关的 AP，为每个命中的 AP 生成防护测试用例。
> 目的：把历史踩坑转化为回归防护网，不重蹈覆辙。

## 触发时机

Phase 5 测试方案编写时，在常规 AC 用例编写**之后**执行。

## 执行流程

### Step 1: 确定扫描范围

```
1. 读取 knowledge-map.yaml → module_baselines → 本模块的 core_aps
2. 读取 anti-patterns.md Phase 3 + Phase 5 分组（编码+测试相关）
3. 用 requirement.md 的关键词匹配 AP.触发信号
```

### Step 2: 逐条评估

对每个命中的 AP：

| 评估项 | 判定 |
|--------|------|
| 本次改动是否触及该 AP 的触发信号？ | 是 → 继续 / 否 → 跳过 |
| 现有测试用例是否已覆盖该 AP 的防护场景？ | 是 → 标记"已覆盖" / 否 → 生成补充用例 |
| 防护用例的测试方法是什么？ | 单测 / 集成测试 / E2E / 仅代码审查 |

### Step 3: 生成补充用例

每个需补充的 AP 生成 1 个防护测试用例，格式：

```markdown
### TC-AP-{AP编号} {AP 检查指令}（防护用例）

| 项 | 内容 |
|----|------|
| **来源** | AP-{编号}（CASE-{ID}：{一句话教训}） |
| **场景** | {触发该反模式的具体场景} |
| **操作** | {测试操作} |
| **预期** | {正确行为，即防护成功} |
| **反预期** | {如果防护失败会怎样——来自 CASE 的真实后果} |
| **覆盖层** | {前端/Service/SQL/配置/...} |
```

### Step 4: 输出到测试方案

在 test-plan.md 新增章节：`## 反模式防护用例（AP-Driven）`

包含：
- AP 扫描命中清单（已覆盖 / 需补充）
- 补充的防护用例
- 覆盖度统计

## AP 可测试性分类

不是所有 AP 都能转化为自动化测试用例：

| 类型 | 说明 | 测试方法 | 占比 |
|------|------|---------|------|
| **可单测** | 输入→输出可断言 | Mockito + Assert | ~40% |
| **可集成测试** | 需 DB/外部服务 | H2 + TestContainer | ~20% |
| **仅代码审查** | 架构/命名/风格类 | Phase 4 六层追踪 | ~30% |
| **仅 E2E** | 需完整环境 | Phase 9 浏览器验证 | ~10% |

Phase 5 只产出"可单测"和"可集成测试"的用例。"仅代码审查"和"仅 E2E"标记为 Phase 4/9 覆盖。
