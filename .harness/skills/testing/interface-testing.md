# 接口测试技能（门禁3：5 维度覆盖）

> 验证服务间交互的正确性，弥补单元测试 Mock 了外部依赖的盲区。
> 来源：FDE 产出质量保障测试方案 · 门禁3。
> 阈值标准：`rules/code-quality-gates.md` §门禁3。

## 触发条件

Phase 5 中，当任务满足以下任一条件时**必须加载本 skill**：

- 新增 API 接口（Controller / RPC Provider）
- 修改已有接口的请求/响应结构
- 修改接口权限规则
- 新增/修改外部系统调用（HTTP / Dubbo / MQ）
- 涉及数据一致性的写操作接口

**跳过条件**：纯前端展示改动 / 纯配置变更 / 不涉及接口交互。

---

## 5 维度测试矩阵

### 维度 1：契约一致性

**验证什么**：请求/响应是否符合接口文档 Schema。

| 检查项 | 示例 | 阻断 |
|--------|------|------|
| 字段类型匹配 | 文档 string 实际 number | ✅ |
| 必填项完整 | 文档 required 实际缺失 | ✅ |
| 枚举值范围 | 文档 enum=["A","B"] 实际返回 "C" | ✅ |
| 字段命名一致 | 文档 userId 实际 user_id | ✅ |
| 响应码语义正确 | 成功 200 / 创建 201 / 参数错 400 / 未授权 401 | ⚠️ 告警 |

**测试方法**：
```
1. 从接口文档（Swagger/OpenAPI/手写 Schema）提取 Schema
2. 发送正确请求 → 验证响应 Schema 100% 匹配
3. 关注：嵌套对象、数组元素类型、nullable 字段
```

### 维度 2：业务逻辑

**验证什么**：正向流程 + 异常分支。

| 场景 | 最低覆盖 |
|------|---------|
| 正向（happy path） | 每个接口 ≥ 1 |
| 参数缺失 | 每个 required 字段 ≥ 1 |
| 参数越界 | 数值/长度/格式非法 ≥ 1 |
| 业务规则违反 | 状态不允许/余额不足/超期限 ≥ 1 |
| 重复操作 | 重复创建/重复提交 ≥ 1 |

**测试方法**：
```
1. 正向：标准输入 → 验证返回数据正确 + DB 状态正确
2. 参数缺失：去掉必填字段 → 验证返回 400 + 错误信息清晰
3. 业务违规：构造不满足前置条件的数据 → 验证拒绝 + 状态未变更
```

### 维度 3：权限校验

**验证什么**：鉴权和越权场景。

| 场景 | 期望行为 | 阻断 |
|------|---------|------|
| 无 token / 无效 token | 401 Unauthorized | ✅ |
| token 过期 | 401 + 明确过期提示 | ✅ |
| A 用户操作 B 的数据 | 403 Forbidden | ✅ |
| 普通用户调管理员接口 | 403 Forbidden | ✅ |
| 有权限的正常访问 | 200 + 正确数据 | ✅ |

**测试方法**：
```
1. 准备至少 2 个不同角色的用户（admin + normal）
2. 无 token 请求 → 断言 401
3. normal 用户请求 admin 接口 → 断言 403
4. A 用户请求 B 用户的资源 → 断言 403 或空结果（取决于设计）
5. 有权限请求 → 断言 200 + 数据与权限范围一致
```

### 维度 4：幂等性

**验证什么**：重复请求是否安全。

| 接口类型 | 幂等要求 | 验证方式 |
|---------|---------|---------|
| GET / 查询 | 天然幂等 | 跳过 |
| POST / 创建 | 必须有防重 | 同一请求发两次，验证只创建一条 |
| PUT / 全量更新 | 天然幂等 | 同一请求发两次，结果一致 |
| PATCH / 局部更新 | 需验证 | 同一操作重复执行，状态不变 |
| DELETE / 删除 | 需验证 | 删除不存在的资源，返回 404 或 200（不报错） |

**测试方法**：
```
1. 创建类：带相同幂等 key 发两次 → 断言只创建 1 条记录
2. 更新类：同一 PUT 发两次 → 断言数据相同、version 不变或 +1（取决于设计）
3. 删除类：删除同一资源两次 → 第二次不报 500
4. 并发场景：2 线程同时提交 → 只有 1 个成功（乐观锁/唯一索引）
```

### 维度 5：向前兼容

**验证什么**：新版本是否破坏现有调用方。

| Breaking Change 类型 | 检查方式 | 阻断 |
|---------------------|---------|------|
| 删除字段 | 对比新旧 Schema diff | ✅ 未声明则阻断 |
| 修改字段类型 | Schema diff | ✅ |
| 修改必填性（optional → required） | Schema diff | ✅ |
| 修改枚举值（删除选项） | Schema diff | ✅ |
| 新增必填请求参数 | Schema diff | ✅ |
| 新增可选字段 | — | ⚠️ 不阻断 |

**测试方法**：
```
1. 用旧版客户端的请求格式调新版接口 → 断言仍能正常工作
2. 新版响应中旧字段仍存在 → 断言不丢字段
3. 如果有 breaking change → 必须在 CHANGELOG 中显式声明 + 协调调用方升级
```

## 执行流程

```
Step 1: 识别接口变更
  → git diff 中筛选 Controller / Provider / DTO 文件
  → 列出本次新增/修改的接口清单

Step 2: 逐接口编写测试
  → 每个接口按 5 维度矩阵编写用例
  → 填写覆盖矩阵表

Step 3: 执行测试
  → 运行接口测试（MockMVC / RestAssured / httpie）
  → 收集通过/失败结果

Step 4: 输出覆盖报告
  → 写入 changes/<req>/interface-test-report.md
```

## 覆盖矩阵模板

每个接口必须填写此表（嵌入 `changes/<req>/interface-test-report.md`）：

```markdown
## 接口测试覆盖矩阵

| 接口 | 契约 | 业务逻辑 | 权限 | 幂等 | 兼容 | 结论 |
|------|------|---------|------|------|------|------|
| POST /api/xxx | ✅ | ✅(3用例) | ✅ | ✅ | N/A(新接口) | PASS |
| PUT /api/yyy | ✅ | ✅(2用例) | ✅ | ✅ | ✅(无breaking) | PASS |
| GET /api/zzz | ✅ | ✅(1用例) | ✅ | N/A | ✅ | PASS |

### 未覆盖说明（如有）
- 接口 A 幂等性未测试，原因：纯查询接口
```

## 交付物清单

| 产物 | 说明 | 必须 |
|------|------|------|
| 接口测试用例代码 | 每个接口至少覆盖：正向 + 参数异常 + 权限异常 | ✅ |
| 测试数据方案 | 测试数据如何准备和清理，不污染其他环境 | ✅ |
| 接口文档同步 | 新增/变更接口必须同步更新文档 | ✅ |
| 覆盖矩阵表 | 5 维度覆盖情况 | ✅ |
| Breaking Change 声明 | 如有不兼容变更，必须在 MR 描述中声明 | 条件 |

## 门禁判定

```
ALL of:
  ✅ 接口测试通过率 = 100%
  ✅ 每个新增/变更接口在覆盖矩阵中有记录
  ✅ 覆盖矩阵无「未覆盖且无说明」的空格
  ✅ 无未声明的 breaking change
→ 门禁3 PASS

ANY of:
  ❌ 有接口测试失败
  ❌ 新增接口无测试覆盖
  ❌ 契约不一致（Schema 不匹配）
  ❌ 有 breaking change 未声明
→ 门禁3 FAIL → 阻断，回退修复
```

## 技术选型参考

| 语言/框架 | 推荐测试工具 | 说明 |
|----------|------------|------|
| Java/Spring Boot | MockMVC + RestAssured | MockMVC 内存级，RestAssured HTTP 级 |
| Node.js/Express | Supertest + Jest | 内存级请求 |
| Python/FastAPI | httpx + pytest | AsyncClient 内存级 |
| 通用 | Postman/Newman + Schema Validator | 黑盒级 |

## 与单元测试的关系

| 维度 | 单元测试（门禁2） | 接口测试（门禁3） |
|------|----------------|----------------|
| 粒度 | 方法级 | 接口级 |
| 外部依赖 | 全部 Mock | 部分真实（DB 可用 H2） |
| 验证重点 | 逻辑正确性 | 交互正确性 + 契约 |
| 执行速度 | 毫秒 | 秒-分钟 |
| 前置 | 门禁1 通过 | 门禁1 + 门禁2 通过 |
