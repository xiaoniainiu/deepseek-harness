# TDD Loop — 红灯→绿灯→重构→验证

> Phase 3/5 编码和测试阶段的核心执行方法。

## 铁律

```
没有失败的测试，就不写生产代码。
```

## Red-Green-Refactor-Verify

### RED — 写失败测试

1. 读 task 的 `testDescription`
2. 在 `testFile` 指定的位置写测试
3. 运行测试 — **必须失败**
4. 确认：失败是因为功能缺失（不是语法错误）

### GREEN — 最小实现

1. 写让测试通过的最简代码
2. 运行测试 — **必须通过**
3. 不添加测试未要求的功能

### REFACTOR — 清理（可选）

1. 消除重复，改善命名
2. 每次修改后跑测试 — 保持绿灯
3. 不添加新行为

### VERIFY — 全面质量检查

1. 运行 task 的所有 `verificationCommands`
2. 运行 plan.json 的所有 `qualityCommands`
3. 读完整输出 — 不跳过，不猜测
4. **全部通过才能提交**

## 规则

- **一次一个测试** — 不要预先写所有测试
- **看它失败** — 测试马上通过说明测试无用
- **最小代码** — 只够通过当前测试
- **真实代码** — 除非依赖真正外部系统，否则不 mock
- **失败立修** — 测试红灯时不做别的事

## 红旗 — 停下来修正

| 信号 | 问题 | 动作 |
|------|------|------|
| 测试没写就写了代码 | 违反 TDD | 删代码，先写测试 |
| 测试马上通过 | 测试无效 | 修测试，让它先红 |
| "应该能过"没跑 | 幻觉风险 | 跑命令 |
| 一口气写完所有测试 | 失去 TDD 节奏 | 写一个，实现，再下一个 |

## 适用范围

- **backend / integration 任务**: 全面 TDD
- **UI 任务**: 不强制 TDD，用 typecheck + lint + build 验证
- **修 bug**: 先写复现 bug 的测试（红），修复（绿）
