# 深度工作协议

> 资深工程师不是"查规则 → 写代码"，而是"建立心智模型 → 推理 → 实现 → 反思"。
> Pre-flight 防遗漏，本协议**防误解**。
> 来源：OpenSpec（spec-driven + verify + living-spec）。

## 与现有机制的关系

| 机制 | 作用 | 层级 |
|------|------|------|
| Pre-flight（已有） | 清单式："我知道什么 / 不知道什么" | 安全网（L0） |
| Confidence Gate（已有） | 决策点拦截：LOW 时停止 | 安全网（L0） |
| **心智模型（本文件 §1）** | 叙事式："数据从 A 流到 B，经过 C 校验" | **深度思考** |
| **检查点反思（本文件 §2）** | 意图驱动："做的是否是想做的" | **深度思考** |
| **意图验证（本文件 §3）** | Phase 3 结束门禁："完整/正确/一致" | **深度思考** |
| **体验对照（本文件 §4）** | 回旋镖："计划的体验 vs 实际体验" | **深度思考** |

执行顺序：Pre-flight → 心智模型 → (编码) → 检查点反思 → (下一层) → ... → 意图验证 → 体验对照

## §1 心智模型构建

**时机**：每个 Task 开始时，Pre-flight 之后。

Pre-flight 回答"我知道什么"，心智模型回答"我理解什么"。

```markdown
## Mental Model: {Task 标题}

### 数据流：谁产生 → 谁消费 → 怎么流转
→ {一句话描述数据从用户操作到持久化的完整路径}
→ {标注关键转换点：校验、转换、分支}

### 状态变迁：改变了什么 → 触发什么副作用
→ {这个 Task 会改变哪些实体的状态}
→ {状态变化会触发的连锁反应：通知、审批流、其他模块更新}

### 不变量：什么必须保持不变
→ {列出不能被这个 Task 破坏的系统不变量}
→ {例：已审批的资产不能被反向修改状态}

### 边界：我改的范围 vs 不能碰的范围
→ {明确改动边界}
→ {标注"诱惑区"——看起来应该一起改但不在范围内的地方}
```

### 与 Pre-flight 的区别

| 维度 | Pre-flight | 心智模型 |
|------|-----------|---------|
| 形式 | 清单（知道/不知道/盲区） | 叙事（A → B → C 的故事） |
| 回答的问题 | "我缺什么信息？" | "我理解系统是怎么工作的吗？" |
| 发现的问题 | 信息缺失 | 理解错误 |
| 触发动作 | 查知识源 / 问用户 | 修正心智模型 / 重新审视方案 |

### L4 修复型的简化

L4 修复型可跳过完整心智模型，但仍需一句话描述数据流：
- "用户点击 {按钮} → 调用 {API} → 执行 {SQL} → 返回 {结果}"

## §2 检查点反思

**时机**：每个架构层完成后（替代原有机械 checklist）。

```markdown
## Checkpoint: {Layer 名称} 完成

### 意图对照
- 原始意图：{requirement.md 中这一层要解决的问题}
- 实际实现：{一句话描述实际做了什么}
- 偏差：{None / 描述偏差及原因}

### 发现
- 实现过程中发现了什么新的理解？
- 这个发现是否需要更新 requirement.md？{是 → 触发 living-spec / 否}

### 下一层预判
- 下一层实现时，这一层的什么决策会产生约束？
- 有没有"在这一层先这样做，下一层再说"的临时决策？{有 → 标记}
```

### 执行纪律

1. **每层完成后必须输出 Checkpoint**（L1/L2/L3 强制，L4 跳过用原 checklist）
2. **发现偏差时当场决策**，不是"继续做完再回头改"：
   - 偏差可接受 → 记录理由 → 继续
   - 偏差不可接受 → 触发 `living-spec.md` → 调整后续任务
3. **临时决策必须标记**，不能默默做了技术决策不记录
4. **机械验证降级为附属**：编译通过/无新 warning/匹配风格 仍然执行，但不再是独立步骤

### 偏差的判断标准

| 偏差类型 | 处理 |
|---------|------|
| 措辞差异（实现了相同语义但用了不同名称） | 可接受，记录 |
| 技术路径差异（用方式 B 代替方案说的方式 A，效果等价） | 可接受，记录理由 |
| 功能缩减（方案说做 3 个场景，只做了 2 个） | 不可接受 → living-spec 或补实现 |
| 功能膨胀（顺手加了方案没说的功能） | 不可接受 → 删除或追加到 requirement |
| 行为偏差（实现的行为与方案描述不一致） | 不可接受 → 修复 |

## §3 意图验证门禁

**时机**：Phase 3 所有 Task 完成后，Phase 4 评审开始前。

```markdown
## Intent Verification: {需求标题}

### 完整性（Completeness）
requirement.md 中列出的每个功能点都已实现？

| 功能点 | 实现位置 | 验证方式 | 状态 |
|--------|---------|---------|------|
| {功能 1} | {文件:行号} | {命令/截图} | ✅/❌ |
| {功能 2} | ... | ... | ... |

### 正确性（Correctness）
实现是否匹配需求**意图**（不只是字面描述）？

检查清单：
- [ ] 有没有"技术上正确但业务上错误"的实现？
  - 例：requirement 说"禁止 X"，实现是 UI 隐藏按钮但 API 仍可调用 → 不正确
- [ ] 有没有"做了但没做对"的功能？
  - 例：排序功能实现了但方向搞反
- [ ] 边界场景的处理是否符合业务规则？

### 一致性（Coherence）
设计决策是否在代码中一致体现？

- [ ] 方案说用方式 A，代码确实用了方式 A？（无 Checkpoint 中标记的未解决偏差）
- [ ] 各层数据模型一致？Entity ↔ DTO ↔ VO ↔ 前端 Model
- [ ] 命名一致？同一概念在各层用同一名称
```

### 门禁规则

- 三项（完整性/正确性/一致性）全部 PASS → 进入 Phase 4
- 任一 FAIL → 修复 → 重新验证
- 不可跳过（与 Phase 状态机的 `Phase 3 → Phase 4` 转换绑定）

## §4 体验对照（Experience Delta）

**时机**：意图验证通过后，Phase 4 评审开始前。
**触发**：L1/L2 强制，L3 涉及 UI 时触发。

> 回旋镖模式：Phase 2 的设计质量评审描述了预期用户旅程，Phase 3 结束时对照实际。

```markdown
## Experience Delta

### 用户旅程对照
| 步骤 | Phase 2 预期 | Phase 3 实际 | 差距 |
|------|------------|------------|------|
| 入口 | {预期入口} | {实际入口} | {None/描述} |
| 步骤 1 | {预期操作} | {实际操作} | ... |
| 步骤 N | {预期结果} | {实际结果} | ... |

### 操作效率对照
- 预期步数：{N} 步
- 实际步数：{M} 步
- 差距原因：{如有差距}

### 差距处理
- 差距 ≤ 可接受 → 记录，进入 Phase 4
- 差距 > 可接受 → 记录到 living-spec → 修复或与用户确认接受
```

**验证方式**（如有浏览器环境）：
- 实际走一遍用户操作路径
- 截图关键步骤
- 对照 Phase 2 设计质量评审中的用户旅程描述
